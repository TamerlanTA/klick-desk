# Защита Task 6 — Server Data, Caching & Firebase Auth

## Первая минута

«Я добавил Firebase Authentication: вход по email/паролю и через Google, регистрацию с подтверждением пароля и защищённый профиль с email и UID. Состояние входа хранит AuthContext: он подписан на onAuthStateChanged, поэтому после F5 сессия восстанавливается, а ProtectedRoute ждёт loading и только потом решает, пускать ли на /profile. Ключи лежат в .env.local. Для данных сделан кэш: ответы API задач кэшируются по ключам на 60 секунд и сбрасываются после любого создания, изменения или удаления, а популярные фильмы TMDB кэшируются в localStorage на час — баннер показывает, откуда они, а Refresh идёт в API мимо кэша.»

## Демонстрация

Открыть https://tamerlanta.github.io/klick-desk/ :

1. **Гость.** В меню справа «Вход» и «Регистрация». Ввести в адрес `/profile` → сразу `/login` (ProtectedRoute).
2. **Регистрация.** «Регистрация» → пароли разные → «Пароли не совпадают». Пароль из 3 символов → «не короче 6». Нормальные данные → сразу `/profile`: email, UID, «Email и пароль». В меню — email и «Выйти».
3. **Ошибки Firebase.** Выйти, на `/signup` ещё раз тот же email → «Такой email уже зарегистрирован». На `/login` неверный пароль → «Неверный email или пароль».
4. **Вход и возврат.** Войти правильно → `/profile`. Нажать F5 — всё ещё вошли (persistence). Открыть `/login` — перекинуло в профиль (GuestRoute).
5. **Выход.** «Выйти» → `/login`, в меню снова «Вход». Страница не перезагружалась.
6. **Google.** «Войти через Google» → окно Google → профиль, «Способ входа: Google».
7. **Кэш задач.** `/tasks`: открыть страницу 2, вернуться на 1 — список появляется мгновенно, без «Загружаем…» (из кэша). Отметить задачу выполненной — кэш сброшен, список и `/dashboard` показывают новое значение.
8. **Фильмы из API.** `/movies` впервые → «Загружаем…» → баннер «Загружено из API · сохранено HH:MM».
9. **Повторный визит.** Уйти на другую страницу и вернуться (или F5) → «Показано из кэша», то же время сохранения. DevTools → Application → Local Storage → `klick-desk.movies.v1` = `{ timestamp, movies }`.
10. **Refresh.** Нажать Refresh → снова «Загружено из API», время обновилось.

## Объяснение простыми словами

- **onAuthStateChanged.** Firebase сам хранит сессию в браузере. При старте приложения мы подписываемся на изменения: Firebase вызывает колбэк с пользователем (или `null`) сразу после проверки сессии, а потом — при каждом входе/выходе. Колбэк кладёт пользователя в state контекста, и весь интерфейс перерисовывается. Функция отписки возвращается из effect как cleanup.
- **Зачем `loading`.** Сразу после F5 Firebase ещё не знает, есть ли сессия: `user` пока `null`. Если бы ProtectedRoute решал сразу, вошедшего выкидывало бы на `/login`. Поэтому `loading = true` до первого ответа, и в это время показываем «Проверяем вход…».
- **Почему контекст, а не пропсы.** `user` нужен в NavBar, ProtectedRoute, GuestRoute, Login, Signup, Profile — на разных уровнях дерева. Context даёт его любому компоненту через `useAuth()` без передачи через все промежуточные компоненты.
- **ProtectedRoute.** Это маршрут-обёртка без пути: три варианта — `loading` → ждём; нет `user` → `<Navigate to="/login" replace state={{ from: location }} />`; есть `user` → `<Outlet />`, то есть сама страница профиля.
- **Navigate и state.from.** `Navigate` — компонент, который при рендере делает переход. `replace` заменяет запись истории, чтобы Back не возвращал на закрытую страницу. В `state.from` лежит адрес, куда гость хотел попасть. После входа GuestRoute читает `location.state.from` и возвращает туда.
- **Почему конфиг в `.env.local`.** Ключи не попадают в исходники и в git, их можно сменить без правки кода, у каждого разработчика свой проект. Vite подставляет только переменные с префиксом `VITE_`. Честно: в собранном JS они видны — это нормально для Firebase Web (доступ защищают правила Firebase и разрешённые домены).
- **Регистрация vs вход.** `createUserWithEmailAndPassword` создаёт нового пользователя в Firebase (и сразу входит), `signInWithEmailAndPassword` проверяет существующего. Пароль уходит в Firebase по HTTPS, мы его нигде не храним: ни в state после отправки, ни в localStorage.
- **Кэш задач.** `cachedQuery(key, fetcher, ttl)`: ключ превращается в строку `JSON.stringify(["tasks","list",{...}])`. Есть свежая запись → вернуть её. Нет → вызвать API и сохранить `{ data, savedAt }`. `invalidateQueries(["tasks"])` удаляет все записи, ключ которых начинается с `"tasks"`. Это та же идея, что query keys и invalidation в TanStack Query, но в 30 строках.
- **TTL-кэш фильмов.** В localStorage лежит `{ timestamp, movies }`. «Свежий» = `Date.now() - timestamp < MOVIES_TTL_MS` (3 600 000 мс). Свежий → показываем без запроса («из кэша»). Старый или нет → запрос в TMDB, сохраняем новый timestamp («из API»). Refresh ставит `force: true` и меняет `id` запроса, effect запускается снова и пропускает проверку кэша.
- **«Из кэша» vs «из API».** Из API — данные только что пришли по сети, timestamp = сейчас. Из кэша — сети не было, показаны сохранённые данные и время, когда их сохранили.
- **Устаревшие запросы.** Каждый effect создаёт `AbortController` и флаг `active`. Cleanup (смена фильтра, второй Refresh, уход со страницы) отменяет запрос, и поздний ответ не пишет в state и не попадает в кэш.

## Вопросы на защите

1. **Как Firebase узнаёт после F5, что я уже вошёл?** SDK хранит токен сессии в IndexedDB браузера (persistence `local` по умолчанию). При запуске он проверяет его и вызывает колбэк `onAuthStateChanged` с пользователем. До этого момента `loading = true`.
2. **Зачем AuthContext, а не пропсы?** Пользователь нужен во многих местах на разной глубине (меню, защищённые маршруты, формы). Контекст избавляет от передачи `user` через каждый уровень.
3. **Что будет, если гость откроет `/profile` напрямую?** Сначала «Проверяем вход…», после ответа Firebase (`null`) ProtectedRoute рендерит `<Navigate to="/login" replace state={{ from }} />`. После входа GuestRoute вернёт на `/profile`.
4. **Где хранится пароль?** Нигде у нас. Он есть в state формы, пока пользователь печатает, затем уходит в Firebase по HTTPS. Firebase хранит хеш пароля на сервере, а в браузере — только токен сессии. В localStorage его нет.
5. **Как кэш понимает, что час прошёл?** При сохранении пишется `timestamp = Date.now()`. При чтении сравниваем `Date.now() - timestamp` с `MOVIES_TTL_MS = 60 * 60 * 1000`. Больше — кэш устарел, идём в API.
6. **Что будет, если API недоступен, а кэш есть?** Если кэш свежий — запроса нет вообще. Если устарел — пытаемся сходить в API; при ошибке показываем старый кэш с баннером «Показано из кэша» и текстом ошибки. Без кэша — сообщение и «Повторить».
7. **Почему ключ TMDB в `.env`, а не в коде?** Чтобы он не попал в git и исходники, и чтобы его можно было заменить без правки кода. За хардкод ключа снимают баллы. В собранном JS переменные `VITE_` всё равно видны — для настоящей защиты ключа нужен свой сервер-прокси.
8. **Чем регистрация отличается от входа на уровне Firebase?** `createUserWithEmailAndPassword` создаёт аккаунт (ошибка, если email занят, или пароль короче 6), `signInWithEmailAndPassword` проверяет существующий (ошибка `auth/invalid-credential`). Оба после успеха входят и вызывают `onAuthStateChanged`.
9. **Когда сбрасывается кэш задач?** После create/update/remove (все ключи `["tasks", …]`), по кнопкам обновления, через 60 секунд (TTL) и при перезагрузке страницы.
10. **Зачем query key — массив с параметрами?** Чтобы разные запросы не перепутались: страница 1 и страница 2, фильтр «Учёба» и «Контент» хранятся отдельно. А общий префикс `"tasks"` позволяет сбросить всё одной командой.
11. **Как устроен вход через Google?** `signInWithPopup(auth, new GoogleAuthProvider())` открывает окно Google; после согласия Firebase создаёт/находит пользователя и вызывает `onAuthStateChanged`. Домен сайта должен быть в Authorized domains.
12. **Почему выход без перезагрузки?** `signOut` меняет состояние Firebase → колбэк ставит `user = null` → React перерисовывает меню, а ProtectedRoute уводит на `/login`. `window.location.reload()` не нужен.

# Защита Task 5 — Routes

## Первая минута

«Я перевёл Klick Desk на React Router. App.jsx теперь только описывает маршруты: общий RootLayout с меню и Outlet, вложенный раздел /tasks со списком и карточкой /tasks/:id, дашборд, About, Login и своя 404. Фильтры списка живут в URL через useSearchParams, карточка берёт ID из useParams и сама загружает задачу из API, четыре страницы грузятся лениво через React.lazy и Suspense. На GitHub Pages прямые ссылки и обновление работают благодаря 404-фолбэку.»

## Демонстрация

Открыть https://tamerlanta.github.io/klick-desk/ и идти по порядку:

1. **Главная → меню.** Нажать «Задачи», «Дашборд», «О проекте». Показать: страница не перезагружается (вкладка браузера не мигает), активный пункт меню подсвечен синим.
2. **Список и фильтры в URL.** На `/tasks` выбрать «Учёба», статус «Готово», сортировку «По названию». Показать адресную строку: `?category=Учёба&status=completed&sort=title...`. Перейти на страницу 2, затем сменить фильтр — `page` пропадает, снова первая страница.
3. **Обновление и ссылка.** Нажать F5 — фильтры остались. Скопировать адрес в новую вкладку — та же выборка.
4. **Карточка.** Открыть задачу: адрес `/tasks/seed-…`, восемь полей. Нажать «← Назад» — вернулись к тому же отфильтрованному списку. Открыть ещё раз, «Все задачи» — список без фильтров.
5. **Несуществующий ID.** Вручную ввести `/tasks/abc` → «Задача не найдена», приложение не падает, меню и таймер на месте.
6. **Дашборд.** Показать 4 карточки статистики, нажать «Агентство» — все числа пересчитались. Нажать на «Просрочено» — открылся список с `status=active&sort=dueDate`. Нажать на просроченную задачу — её карточка.

8. **Обновление на вложенном маршруте.** На `/tasks/seed-001` и на `/dashboard` нажать F5 — страница открылась та же. Кнопки браузера Back/Forward листают историю.
9. **Старое работает.** Создать задачу, отредактировать, отметить выполненной, удалить с подтверждением; «Проверить ошибку API» → «Повторить»; таймер не сбрасывается при переходе список ↔ карточка.

## Объяснение простыми словами

- **Зачем роутер.** Раньше всё было одним экраном, и «какая страница открыта» хранилось в useState. Теперь это адрес: его можно сохранить, отправить, обновить, пройти Back/Forward. Роутер читает адрес и решает, какой компонент показать.
- **Вложенные маршруты и Outlet.** `<Route element={<RootLayout />}>` — родитель. Его дети (`/about`, `/tasks`, …) рисуются на месте `<Outlet />`. Так меню и подвал пишутся один раз. У `/tasks` свой макет `TasksLayout` (маскот, таймер, погода) и свои дети: `index` — список, `:id` — карточка. При переходе между детьми макет не размонтируется, поэтому таймер продолжает идти.
- **useParams vs useSearchParams.** `useParams` — часть пути, которая определяет *какую* страницу показать: `/tasks/:id` → `{ id: "seed-001" }`. `useSearchParams` — необязательные параметры после `?`, которые *настраивают* страницу: фильтры, сортировка, номер страницы.
- **Почему фильтры в URL, а не в useState.** useState живёт в памяти и пропадает при обновлении/закрытии. URL переживает F5, им можно поделиться, Back возвращает предыдущий фильтр. Изменение URL вызывает новый рендер, а effect списка видит новые значения в зависимостях и делает запрос.
- **Некорректный URL.** Хук `useTaskFilters` проверяет каждый параметр по списку допустимых значений (`CATEGORIES`, `SORT_OPTIONS`, `[6, 12, 24]`, целое > 0). Мусор заменяется значением по умолчанию, поэтому страница не ломается.
- **Link и NavLink.** `<a href>` заставляет браузер заново скачать страницу — состояние и таймер теряются. `<Link>` меняет адрес через History API, и React перерисовывает только нужную часть. `NavLink` — тот же Link, но знает, активен ли он, и добавляет класс `active`. `end` у «/» нужен, иначе главная была бы «активна» на любом адресе.
- **React.lazy + Suspense.** `lazy(() => import("./pages/DashboardPage.jsx"))` — Vite выносит страницу в отдельный файл, он скачивается при первом заходе. Пока файл грузится, компонент «приостанавливается», и ближайший `<Suspense>` показывает fallback «Загружаем страницу…». Suspense стоит в RootLayout вокруг Outlet — меню остаётся на экране.
- **basename.** Сайт лежит не в корне домена, а в `/klick-desk/`. `basename` говорит роутеру: «эту часть адреса не считай маршрутом». Значение берётся из `import.meta.env.BASE_URL`, то есть из `base` в `vite.config.js`, — они не разъедутся.
- **Почему нужен 404-фолбэк.** GitHub Pages — просто хранилище файлов. По адресу `/klick-desk/tasks/seed-001` файла нет, и сервер отдаёт `404.html`. В нём скрипт превращает путь в `/klick-desk/?p=tasks/seed-001` и открывает `index.html`. Скрипт в `index.html` до запуска React делает `history.replaceState` обратно на `/klick-desk/tasks/seed-001`, и роутер показывает карточку. В DevTools этот первый ответ виден как 404 — это нормально.
- **Карточка и устаревшие запросы.** ID из `useParams` передаётся в `TaskDetails` с `key={id}`. Effect `[id, revision]` делает `taskApi.get(id)`. При смене ID cleanup ставит `active = false` и вызывает `abort()`, поэтому поздний ответ старой задачи не перезапишет новую.
- **Нет задачи vs ошибка.** API бросает ошибку с `name = "NotFoundError"`. Её показываем как «Задача не найдена» без кнопки повтора. Случайная сетевая ошибка (5%) — сообщение и «Повторить».
- **Дашборд.** Один запрос `taskApi.listAll()` → массив задач в state. Статистику считает обычная функция `getDashboardStats(tasks, category)` на каждом рендере. Фильтр — useState: клик меняет категорию → новый рендер → новые числа, без нового запроса.
- **Back в карточке.** Ссылка на задачу в списке передаёт `state={{ backTo: "/tasks?..." }}`. Карточка читает `location.state.backTo`; при прямом открытии state пустой — возвращаемся на `/tasks`.

## Вопросы на защите

1. **Чем `useParams` отличается от `useSearchParams`?** `useParams` читает сегменты пути из шаблона маршрута (`/tasks/:id` → `id`), это обязательная часть адреса. `useSearchParams` читает и меняет query-строку `?a=1&b=2` — необязательные настройки страницы.
2. **Зачем `Outlet`?** Это место в родительском макете, куда роутер вставляет дочернюю страницу. Без него вложенные маршруты не отрисуются.
3. **Что будет при обновлении страницы на `/tasks/123`?** Браузер запросит этот адрес у GitHub Pages, получит `404.html`, тот перенаправит на `index.html?p=tasks/123`, скрипт вернёт адрес, роутер откроет карточку и она загрузит задачу 123. Если такой нет — «Задача не найдена».
4. **Почему фильтры в URL, а не в `useState`?** Чтобы они переживали обновление, работали с Back/Forward и ими можно было поделиться ссылкой.
5. **Как работает lazy loading и зачем `Suspense`?** `React.lazy` загружает код компонента только при первом рендере. Пока он грузится, нужен запасной UI — его показывает ближайший `Suspense` через `fallback`. Без `Suspense` React выдаст ошибку.
6. **Что будет при невалидном ID?** API ответит `NotFoundError`, страница покажет «Задача не найдена» и ссылки «Назад»/«Все задачи». Неизвестный путь вообще (не `/tasks/...`) ловит маршрут `*` → своя 404.
7. **Чем `Link` отличается от `<a>`?** `<a href>` — полная перезагрузка документа, теряется всё состояние. `Link` отменяет стандартный переход, вызывает `history.pushState` и роутер перерисовывает только изменившуюся часть.
8. **Зачем `basename`?** Приложение опубликовано в подпапке `/klick-desk/`. `basename` убирает этот префикс при сопоставлении маршрутов и добавляет его во все `Link`.
9. **Почему App.jsx без состояний?** По заданию он отвечает только за маршрутизацию. Состояние списка переехало в `TasksPage`, карточки — в `TaskDetailsPage`/`TaskDetails`, общие для раздела таймер и маскот — в `TasksLayout`.
10. **Почему в Task 5 появился собственный хук, если в Task 4 их не было?** Task 4 запрещал собственные хуки, а Task 5 прямо требует папку `hooks/`. `useTaskFilters` — обычная функция, которая вызывает `useSearchParams` и возвращает проверенные фильтры и функцию их изменения. Логика URL вынесена из страницы, чтобы её было легче прочитать.
11. **Что произойдёт при смене фильтра?** `updateFilters` собирает новые параметры, удаляет `page` и вызывает `setSearchParams`. Адрес меняется → `TasksPage` рендерится с новыми `filters` → зависимости effect изменились → cleanup старого запроса и новый `taskApi.list`.
12. **Почему NavLink «Главная» с `end`?** NavLink считает себя активным, если текущий путь *начинается* с его `to`. Любой путь начинается с `/`, поэтому без `end` главная подсвечивалась бы всегда.

## Объяснение

- useState хранит состояние между рендерами; setter планирует новый рендер. Каждый рендер получает снимок значений.
- useEffect синхронизирует компонент с внешней системой после commit. Здесь это запросы API, настройки, интервал и погода.
- Зависимости содержат все реактивные значения, которые читает effect. [] означает отсутствие таких зависимостей, а не гарантию одного вызова в StrictMode.
- Cleanup запускается перед следующим setup и при unmount. Он отменяет запрос/интервал и помечает старый effect неактивным.
- Race condition: запрос A начат раньше B, но ответил позже. active и abort запрещают старому A перезаписать результат B.
- Stale closure: async обработчик продолжает видеть снимок своего рендера. Поэтому ID намеренно фиксируется перед await; результат не применяется к текущему выбранному ID вслепую.
- busy блокирует конфликтующие изменения. Ошибка API не выдаётся за успех, формы сохраняют черновик для повтора.
- Рендер вычисляет JSX; commit применяет изменения к DOM. React сопоставляет элементы по типу и key. Стабильные ID сохраняют правильную идентичность при сортировке и удалении.
- Состояние списка принадлежит App, черновик — TaskForm, подробности — TaskDetails. Данные проходят через props и callbacks.
